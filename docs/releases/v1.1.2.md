# CosmoOS 1.1.2

Images for other hypervisors and for clouds, a first boot configured from
a seed disk, and OpenSSH, curl, git and nano as packages.

## Images for more hypervisors

Beside each architecture's raw image, `cosmoos-ARCH.img`, the release
now has:

- `cosmoos-ARCH.qcow2` and `cosmoos-ARCH.vmdk`, the same live image in
  the formats other hypervisors take.
- `cosmoos-ARCH.iso`, an installer CD for a UEFI virtual machine. Boot it
  with an empty disk attached and run `cosmo-install` on that disk, as
  from the live image.
- `cosmoos-ARCH-cloud.qcow2`, an installed system for a cloud (below).

All of them are in `SHA256SUMS`. See [Installing](../guide/installing.md).

## The cloud image and the seed

`cosmoos-ARCH-cloud.qcow2` is an installed system ready to boot: no
console, no install step.

**It grows to its disk.** Copied to a larger disk, at its first boot it
moves its partition table to the disk's end and grows its root
partition and file system to fill it. `df /` shows the whole disk from
the first command. This also holds for any disk `cosmo-install` wrote
that is copied to a larger one.

**It reads a seed.** A seed is a small disk in cloud-init's NoCloud
layout: an ISO 9660 or FAT volume labelled `cidata` holding `meta-data`,
`user-data` and `network-config`. At every boot, `cosmo-seed` reads a
seed if one is attached:

- `meta-data`: `instance-id` (required) and `local-hostname`.
- `user-data` starting `#cloud-config`: `hostname` and
  `ssh_authorized_keys`.
- `network-config` version 2: a static IPv4 address, gateway and name
  servers per interface, or DHCP.

The host name and keys are applied once per instance id. The network
settings are applied at every boot that has the seed. Other keys are
named and ignored. Without a seed the boot is as before: DHCP, and an
empty `authorized_keys`, so attach a seed with your key or the machine
can be reached only from its console. The seed must be attached as a
disk: there is no CD-ROM driver. `tools/mkseed.py` in the source tree
writes one.

## Packages: OpenSSH, curl, git, nano

The package repository now has software a server needs, built from
pinned upstream sources:

| Package | What |
|---|---|
| `openssh-client` | OpenSSH 10.6: `ssh`, `scp`, `sftp`, `ssh-keygen`, `ssh-keyscan`, `ssh-agent`, `ssh-add` |
| `openssh-server` | OpenSSH's `sshd` |
| `curl` | curl 8.23.0, HTTPS by mbedTLS |
| `git` | git 2.56.1, HTTPS by curl |
| `nano` | nano 9.3 |

On an installed system: `pkg update`, then for example `pkg install
git`. See [Packages](../guide/packages.md).

**OpenSSH's sshd in place of dropbear.** After `pkg install
openssh-server`, run `svc start sshd`. sshd takes port 22 from dropbear
and starts at every boot after. It makes its own Ed25519 host key, so a
client sees a new host key once. It has the same rules as dropbear:
root by key only, from the same `/root/.ssh/authorized_keys`, and no
forwarding. Only Ed25519 keys work: the build has no OpenSSL, so RSA and
ECDSA keys do not. To go back to dropbear, run `svc stop sshd`, then
`pkg remove openssh-server`, then `svc start dropbear`. Removing the
package leaves a running sshd on port 22 until it is stopped or the
machine boots again.

## Upgrading from v1.1.1

`cosmo-upgrade --fetch v1.1.2`, reboot, then `pkg update && pkg
upgrade`. Nothing changes on an installed system whose root already fills
its disk. `cosmo-upgrade --rollback` returns to v1.1.1.

Known:

- `ssh` and `sshd` print `setsockopt ... Protocol not available` lines:
  CosmoOS refuses socket options, and both carry on.
- `ssh` or `scp` from the machine to itself (127.0.0.1) does not end
  after the command or copy is done. Connections from other machines
  end normally.
- A bare `scp` is dropbear's, which cannot copy from this machine (it
  needs dropbear's client, which is not built). Use OpenSSH's,
  `/usr/bin/scp`.

Tested:

- On every change, on both architectures:
  - `make test-images` boots the QCOW2, the VMDK and the ISO, and
    installs from the ISO.
  - `make test-cloud` boots the cloud image on a disk four times its
    size, with a seed and without one.
  - `make test-ports` installs each package with `pkg` on an installed
    system and runs it: an ssh login by key and scp both ways, curl and
    git over HTTPS, nano under a terminal.
- On a Parallels virtual machine upgraded from v1.1.1 to v1.1.2-rc2
  before this release was tagged. See
  [Tested platforms](../guide/platforms.md). There, v1.1.2-rc1's
  `svc start sshd` could not take port 22: dropbear's `select` went on
  after its SIGTERM handler ran, because the kernel restarted calls that
  Linux never restarts (backlog LX-29). rc2 fixes it.
